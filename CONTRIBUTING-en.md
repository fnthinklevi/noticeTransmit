## 4. Branching & Commit Workflow

1. **Fork** this repo and clone it locally.
2. Branch off `main` (or `develop`) with a **focused branch name**:
   - Feature: `feat/short-desc`, e.g. `feat/icon-preview`
   - Fix: `fix/short-desc`, e.g. `fix/battery-cast-crash`
   - Refactor/docs: `refactor/...`, `docs/...`
3. Keep each branch to a single goal — one PR solves one class of problem.
4. Complete local validation before submitting (see Section 7).
5. Open a PR to `main` describing: purpose, scope of impact, and self-testing.
6. Wait for CI (`.github/workflows/analyze.yml`) to pass before merging.

### Commit Message

Follow Conventional Commits:

```
<type>(<scope>): <subject>

<optional body>
```

- `type`: `feat` / `fix` / `refactor` / `docs` / `style` / `test` / `chore`
- `scope` (optional): `flutter` / `android` / `server` / `docs`
- Example: `fix(android): prevent webhook silent failure after in-process service recreate`

## 5. Formatting Gate: One Script, Three Languages

Formatting is no longer just `dart format`. **Local and CI run the same script**, so "green locally, red on CI" cannot happen:

```bash
bash .github/scripts/check_format.sh          # check only, exit 1 on violations
bash .github/scripts/check_format.sh --fix    # fix all three languages in place
```

It covers three toolchains:

| Language | Tool | Scope / config |
|----------|------|----------------|
| Dart | `dart format` (shipped with the Flutter SDK) | `lib test` (note: not just `lib/`) |
| Kotlin | ktlint 1.8.0 standalone CLI (fat jar; does not touch `build.gradle.kts`) | `android/app/src/**/*.kt`, rules in the repo-root `.editorconfig` |
| Server JS | Prettier 3.9.8 | reuses `server/package.json`'s `format` / `format:check` (scope in `server/.prettierignore`) |

> `.editorconfig` deliberately disables ktlint's wrapping rules. The reason is in Section 8.3: this
> repo has many "read the source file and assert on its text" guards, and re-wrapping code would
> silently change what those guards assert.

## 6. Code Style

### 6.1 Flutter / Dart (`lib/`)

- **Must pass** `bash .github/scripts/check_format.sh` and `flutter analyze`. CI fails only when the analyze output contains `error •`; style hints (info/warning) do not block a merge.
- **Null-safety first**: never hard-cast data that may be absent. This project once crashed an entire page due to `rule['type'] as String` when legacy data lacked a field — always read external/stored data with `as Type? ?? default` (e.g. `map['x'] as int? ?? 0`).
- **Theme & colors**: use `AppColors` (Cupertino-style semantic colors, `lib/theme/app_colors.dart`) and `AppThemeColors` (`ThemeExtension`, `lib/theme/app_theme.dart`). **Do not hardcode colors**, or dark mode will break.
- **Cross-platform comms**: Flutter ↔ Android use a single `MethodChannel('com.fnthink.notice/notification')`
  (the Dart constant lives in `lib/services/platform_channel.dart`). The native side is split by
  domain into 5 handlers (`Config` / `Device` / `File` / `Permission` / `Stats` under
  `android/app/src/main/kotlin/com/fnthink/notice/channels/`), **87** method names in total. The
  two-sided contract is pinned by `test/services/channel_method_parity_test.dart` — adding or
  renaming a method requires updating both the Dart call sites and that test's expected total.
- **State & DI**: use the `get_it`-injected Service classes (registered in `lib/di/service_locator.dart`); do not `new` singletons inside Widgets.
- **Logging**: `analysis_options.yaml` enables `avoid_print`; use `debugPrint`.
- For large files (e.g. `main_page.dart`, `rule_edit_page.dart`), ensure changes don't break existing navigation or the bottom SnackBar behavior (`_pushPage` / `_showInfo`).

### 6.2 Android Native (Kotlin, `android/`)

- Coroutines should run on `Dispatchers.IO`; network requests go through `NetworkClient` / `OkHttp`.
- Background logic lives in `NotificationMonitorService` and its modules (`BatteryMonitor` / `NotificationProcessor` / `WebhookSender`, etc.); prefer reusing existing modules over reimplementing.
- Launcher icons: `IconOption` has 17 keys (`lib/services/icon_service.dart`) and the manifest holds **17 icons × 2 locales = 34 `activity-alias`** entries; they must stay strictly aligned. The single maintenance point is `launcherIconCount = 17` in `test/architecture/launcher_manifest_contract_test.dart`; the merged-manifest reality check is `python tools/check_launcher_manifest.py <manifest path>`.
  ⚠ That contract also requires `src/main` to keep a MAIN/LAUNCHER `.MainActivity` (so
  `flutter test integration_test/...` can discover a launch activity) while the release/profile
  variants remove it via manifest overlay. Read that test's comment before touching it — break it and
  you get either "integration tests can't run" or "duplicate launcher icon in production".
- **Android lint is part of the PR gate**: `./gradlew :app:lintDebug` runs with `abortOnError = true`.
  Known false positives are absorbed by `android/app/lint-baseline.xml` (only already-reviewed
  historical entries — **a new error still turns CI red**). Don't add entries to the baseline just to
  go green; fix the code first.
- `onDestroy` must not leave any globally permanent disabled state (this repo already fixed a similar `NetworkClient.isActive` issue).

### 6.3 Server (`server/`, Node.js 24 + Express 5)

- Layout: entry point `server/server.js` (wiring + process lifecycle); logic in `server/lib/`
  — `app.js` (Express assembly and CORS), `middleware.js` (security headers / rate limiting /
  IP blocking / auth), `store.js` (state persistence, crypto, failed-attempt counters),
  `otp.js` (otplib v13 wrapper), `routes/auth.js` (mounted at `/api/admin`),
  `routes/version.js` (version check + admin version endpoints).
- After changes, run:
  ```bash
  cd server
  node --check server.js      # syntax self-check
  npm test                    # HTTP contract tests (jest, 29 cases)
  npm run format:check        # Prettier; or npm run format to fix in place
  npm start                   # run locally and hit /health
  ```
- Changes to admin endpoints (`/api/admin/*`) must preserve auth and request-body validation.
  Version-config writes go through a **whitelist projection** (`VERSION_CONFIG_FIELDS` in
  `routes/version.js`; unregistered keys are never persisted), so a new field must be registered explicitly.
- **Do not hardcode secrets** in code or config; secrets come from environment variables (see Section 9).
- Any new environment variable must be added to the env table in `server/README.md`
  (`server/README-en.md` is its mirror).

## 7. Pre-submit Local Checklist (equivalent to the PR gate)

The PR gate is `.github/workflows/analyze.yml` (16 steps). Running the following in order reproduces it locally:

```bash
# 1) Dart static analysis (errors fail the build)
flutter pub get
flutter analyze --no-pub

# 2) Version / documentation gate (pubspec ↔ update_manager ↔ MainActivity.kt ↔ version.json,
#    plus version.json sha256 completeness, website i18n coverage, l10n zh/en key parity)
bash .github/scripts/check_version_consistency.sh

# 3) Dart unit tests (379 cases / 37 files) + coverage
flutter test --no-pub --coverage

# 4) Android JVM unit tests (234 cases / 26 classes, JDK 21; no signing keys needed)
cd android && ./gradlew :app:testDebugUnitTest --console=plain

# 5) Android lint (debug variant; errors fail the build)
./gradlew :app:lintDebug --console=plain

# 6) Server contract tests (29 cases, Node 24)
cd ../server && npm ci && npm test

# 7) Three-way formatting gate (Dart / Kotlin / JS)
cd .. && bash .github/scripts/check_format.sh
```

Extra things CI does (optional locally):

- Coverage report and upload: `genhtml coverage/lcov.info -o coverage/html`, then uploaded as the
  `coverage-report` artifact.
- **Local and CI share the same analyze verdict**: `flutter analyze --no-pub --fatal-infos`, failing on
  the exit code. The old step only grepped `error •` and let warnings and infos through, which meant the
  lint rules in `analysis_options.yaml` had no gate at all; measured locally the baseline is clean both
  before and after, so tightening costs nothing.
- The `dart_code_metrics` step was **removed** (roadmap E2 / batch ㊶): 4.12.0 pins `analyzer 3.3.1`,
  which reliably throws `Null check operator used on a null value` (exit 255) on Dart 3.12, and the step
  assigned `EXIT_CODE=$?` and never read it ⇒ it could not fail the build by construction.
  **Do not add it back** — the reasoning is in the `analyze.yml` comment.
- The integration smoke test is **not part of the PR gate**, but a `schedule` now runs it every Tuesday
  (batch ㊵; see Section 8.2).

## 8. Test System & Guard Conventions

### 8.1 Test baseline

| Layer | Count | Entry point |
|-------|-------|-------------|
| Dart unit tests | **379 cases / 37 files** | `flutter test --no-pub` (`test/` is grouped into `architecture` / `database` / `models` / `services` / `theme` / `widgets` / `support`) |
| Kotlin JVM unit tests | **234 cases / 26 classes** | `cd android && ./gradlew :app:testDebugUnitTest` (reports under `build/app/test-results/testDebugUnitTest/`) |
| Server contract tests | **29 cases** | `cd server && npm test` (`server/test/auth.test.js`) |
| l10n keys | **861 keys × 2 (zh / en)** | `lib/l10n/arb/app_zh.arb`, `lib/l10n/arb/app_en.arb` |

Run `flutter pub get` before testing. Counts grow with features; if you add or remove tests, update
the numbers above too (they are documentation, not a CI assertion).

### 8.2 On-device tests (manual trigger only)

- `integration_test/smoke_test.dart` is the 7-step main-path smoke test. In CI it runs from
  `.github/workflows/integration_test.yml`, which is **triggered only by `workflow_dispatch`**
  (emulator minutes are billed; it is not attached to PRs).
- Run it locally (real device or emulator required):
  ```bash
  flutter devices                                  # list device ids
  flutter test integration_test/smoke_test.dart -d <device-id>
  ```
- The same workflow also runs the instrumented tests while the emulator is alive:
  `cd android && ./gradlew connectedDebugAndroidTest` (includes `ApkSignatureVerifierInstrumentedTest`).
- If your change affects the launch-entry structure, see the MAIN/LAUNCHER overlay note in 6.2.

### 8.3 Static source guards and duplicated golden fixtures (read before changing behavior)

Many tests in this repo are guards that "read a source file and assert on its text" (contract tests).
When changing an implementation, two real failure modes have already bitten this project:

1. **Shared comment-stripping helpers**: guards must strip comments before asserting, otherwise
   component/method names inside comments pollute the result.
   - Dart: `test/support/source_guards.dart` (`stripComments` / `stripXmlComments` / `blockAfter` / `projectRoot`)
   - Kotlin: `android/app/src/test/java/com/fnthink/notice/SourceGuards.kt` (`stripComments`)
   Reuse them in new guards instead of rolling your own regex. This is also why `.editorconfig`
   (Section 5) disables ktlint's wrapping rules.
2. **Two golden fixtures that must stay byte-identical**:
   - `test/fixtures/rule_engine_golden.json` (read on the Flutter side by `test/services/filter_service_golden_test.dart`)
   - `android/app/src/test/resources/rule_engine_golden.json` (read on the native side by `RuleEngineTest.kt`)

   They are **synchronized copies**, and
   `RuleEngineTest.goldenFixtureCopiesAreIdentical` asserts that both are identical. When you change
   rule-engine / channel behavior you **must update both copies**: editing only one makes the two
   sides run different case sets while both still report green — the hardest kind of fake protection to
   notice. There is also a native-only snapshot
   `android/app/src/test/resources/channel_behavior_golden.json` (read by
   `ChannelBehaviorGoldenTest.kt`); regenerate it per that test's instructions when outbound channel
   behavior changes.
3. **Cross-platform fixtures must be generated, never hand-copied**: the channel
   descriptors used by Dart widget tests come from
   `android/app/src/test/resources/channel_descriptors.json`, which the JVM test
   `ChannelDescriptorExportTest` writes out of `ChannelRegistry` / `AppChannelRegistry`,
   and it fails whenever the file and the production table disagree. **Re-run it after
   editing the channel table.** A hand-maintained copy would only prove two copies agree;
   assertions about form fields and capability-driven visibility would silently stop
   protecting anything.
4. **Reverse-verify every guard**: after adding or changing a guard, deliberately implant the defect it
   is supposed to catch, confirm the guard actually turns red, then revert. If path resolution is wrong
   (`projectRoot()` on the Dart side, the cwd candidate list on the Kotlin side), the assertions may
   never run while the test still reports green.

### 8.4 Localization (l10n)

ARB sources live in `lib/l10n/arb/`; the template is `app_zh.arb` (config in `l10n.yaml`) and the
generated files `lib/l10n/app_localizations*.dart` **are committed to the repo**. Therefore:

```bash
# Must be re-run after editing app_zh.arb / app_en.arb, otherwise CI fails to compile
flutter gen-l10n
```

- The zh / en key sets must match; `bash .github/scripts/check_version_consistency.sh` compares them and fails on drift.
- Commit the generated files too (shipping only the ARB change makes `flutter test` fail to compile on CI).

### 8.5 Database

`lib/database/database_helper.dart` declares `dbVersion = 11`, with 6 tables currently
(`notifications`, `pending_notifications`, `email_channels`, `webhook_channels`,
`webhook_delivery_log`, `app_channels`). Any new table/column must bump `dbVersion` and add an
`onUpgrade` branch; so does a migration that only rewrites the **values** of existing rows (v11
rewrote the delivery keys from localized display names to `chan:<slug>`). Such migrations must be
idempotent and must skip bad rows instead of throwing — an `onUpgrade` exception makes the app
"back up the database and rebuild an empty one", i.e. it wipes the user's history.
`test/database/database_helper_test.dart` pins the version against the schema increments and
forbids literal versions when opening the database during migration. Push history is stored
in SQLCipher (`sqflite_sqlcipher`); keep the encryption semantics when changing it.

## 9. Security & Privacy (Important)

This project is a **notification listener & forwarder**; security and privacy are non-negotiable (full policy: [SECURITY-en.md](SECURITY-en.md)):

- **Notification content is processed and forwarded locally only**, never uploaded to any third-party server (except the Webhook / SMTP targets the user configures).
  Crash reporting (Tencent Bugly) is **off by default**; the SDK is only initialized after the user opts in on the More page, and then uploads minimal data (stack trace, device model, OS version, app version, CPU architecture).
- Do not write notification bodies, SMS bodies, or similar private data into logs, crash reports, or storage. The native diagnostic log (`DiagLog`, toggled by tapping the version number 7 times on the More page, off by default) has a hard rule: **rule names / package names / counters only — never notification titles or bodies**.
- **Server secret management (`.env`)**: `server/.env` is ignored by `.gitignore` and never enters the repo; only `server/.env.example` (placeholders/notes) is committed. The real `.env` is provided locally or via CI Secret. **Never commit production secrets** (`ADMIN_TOKEN_HASH`, `ENCRYPTION_KEY`, etc.). Document any new environment variable in `server/README.md`'s env table.
- Server encryption (`ENCRYPTION_KEY`) must be **64 hex chars** (AES-256-GCM); an invalid format is ignored and the TOTP secret is stored in plaintext — self-check before committing.
- CORS allows only origin-less (native / curl) requests by default; browser cross-origin access requires an explicit `ALLOWED_ORIGINS` allowlist — never `*`.
- Certificate pinning (`CERT_PINS` + `ENABLE_CERT_PINNING`, `--dart-define` on the Dart side) is a
  **framework that ships disabled**. Enablement and rotation are documented in
  `docs/cert_rotation_runbook.md`; never write pin values into a tracked file.

### 9.1 Android Release Signing: PR Work Needs No Keys

APK release signing follows a **zero-secrets-in-source** principle: no Git-tracked source file may contain the keystore path, password, or alias in plaintext.

**What a contributor needs to know**: the signing guard only aborts when the current invocation really
produces a release package. `android/app/build.gradle.kts` decides this from
`gradle.startParameter.taskNames` (assemble / bundle / package + release), because that block runs at
**configuration time** — an unconditional `throw` would also kill `:app:testDebugUnitTest`,
`:app:lintDebug` and the instrumented tests in the PR gate, which never produce a release build and
hold no signing material anyway.

So these commands work fine in an environment with **no keys at all** (they only print a warning):

```bash
cd android
./gradlew :app:testDebugUnitTest --console=plain
./gradlew :app:lintDebug --console=plain
./gradlew connectedDebugAndroidTest          # needs a connected device
```

Only release packaging needs keys, and it **must go through the Flutter entry point**:

```bash
flutter build apk --release --target-platform android-arm64
```

- ⚠ Do **not** use bare `./gradlew :app:assembleRelease` for release builds: `integration_test` is a
  `dev_dependency`, so the release classpath is missing and `GeneratedPluginRegistrant` fails to
  compile. `flutter build apk` wires up plugins and `FLUTTER_TARGET_PLATFORM` (which drives the ABI filter).
- **Local build**: copy `android/key.properties.example` (a keyless placeholder template that is safe to commit) to `android/key.properties` and fill in `storeFile` / `storePassword` / `keyAlias` / `keyPassword`. That file is ignored by both `android/.gitignore` and the root `.gitignore` — **do not commit it**.
- **CI**: only `.github/workflows/build-apk.yml` needs signing material; it injects
  `KEYSTORE_BASE64`, `KEYSTORE_FILE`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` from GitHub
  Actions Secrets and decodes `KEYSTORE_BASE64` into a keystore file for `build.gradle.kts`.
  `analyze.yml` (the PR gate) **holds no signing material by design** — don't add secrets there just to
  make it run a release build.
- **Fail on missing config**: if neither env vars nor `key.properties` exist and the task really is release packaging, `build.gradle.kts` throws a `GradleException`; a lazy `afterEvaluate` + `findByName("packageRelease")` backstop guarantees an unsigned release can never be archived silently. Never replace this with a hardcoded fallback password, and never implement the backstop with `tasks.matching {}` (it materializes matched tasks eagerly — in practice it force-created `assembleRelease` during unrelated calls and broke AGP internals).
- **Rotation**: if the keystore file or password leaks, generate a new keystore immediately and update both the local `key.properties` and CI Secrets. ⚠ In-app updates trust **the signing certificate of the installed app**, so changing keys makes existing users unable to update in-app — read Section 7 of `docs/cert_rotation_runbook.md` (multi-signing transition) before rotating.
- Before committing, run `git status` to confirm no `*.jks` / `*.keystore` / `android/key.properties` file is tracked.

## 10. Release Flow (Standard Release Process)

> Maintainer-only. Every client release must synchronously update the version constants, version config, and artifact archive.

### 10.1 Version number sync (four places + docs)

The version is not only in `pubspec.yaml`. All of the following must match, otherwise `check_version_consistency.sh` fails:

1. `pubspec.yaml` `version: X.Y.Z+NN` (`versionName` and `versionCode` increment together; currently `1.5.74+113`);
2. `_fallbackVersion` / `_fallbackBuild` in `lib/update_manager.dart`;
3. `FALLBACK_VERSION` / `FALLBACK_BUILD` in `android/app/src/main/kotlin/com/fnthink/notice/MainActivity.kt`;
4. `latestVersion` / `latestBuild` in `server/data/version.json`;
5. plus documentation surface: the Version badges in `README.md` / `README-en.md` and the top entry of `update.md`.

```bash
bash .github/scripts/check_version_consistency.sh   # exit 1 on any mismatch
```

### 10.2 Semi-automated release script (recommended)

```bash
bash .github/scripts/release_local.sh <A.B.C>       # e.g. release_local.sh 1.5.74
```

It hardcodes the mechanical steps that are known to work:

- **Stage 0** version-sync preflight (including the `update.md` entry and both README badges);
- **Stage 1** `dart format` (`lib` and `test`) + `flutter analyze` (requires `No issues found`);
- **Stage 2** builds **4 release APKs** one by one: arm64 / arm32 / x86_64 / 3-ABI universal,
  named `notice_arm64_X.Y.Z.apk`, `notice_arm32_X.Y.Z.apk`, `notice_x86_X.Y.Z.apk`,
  `notice_all_X.Y.Z.apk`, archived in `build/app/outputs/flutter-apk/vX.Y.Z/`;
- **Step 6.5** verifies ABI purity via `python` (a single-ABI package must contain exactly one `.so`
  architecture set) and checks versionName;
- **Stage 3** backfills `server/data/version.json`: `latestVersion` / `latestBuild` / `downloads`
  (per-ABI URLs) / `fileSizes` (bytes) / `sha256` (64-hex per ABI), and copies the APKs into
  `server/public/apks/X.Y.Z/`;
- **Stage 4** documentation gap checks (`update.md`, README badges);
- **Stage 5** CI-equivalent self-checks (`flutter test`, `:app:testDebugUnitTest`,
  `check_version_consistency.sh`, format, analyze, `npm test` in `server/`).

**Not covered** (manual): `update.md` / `base.md` wording and audit entries, website content
completeness, git commit/tag, server deployment.

### 10.3 Publish & deploy

1. Commit and tag `vX.Y.Z` → `.github/workflows/build-apk.yml` (tag-triggered) builds the arm64
   package, uploads the artifact, and attaches it to a GitHub Release
   (`softprops/action-gh-release`).
2. Push `server/data/version.json` (and `server/public/**` when needed) to `main` →
   `deploy-pages.yml` publishes the GitHub Pages static fallback (the client first requests
   `/api/version/check`, then falls back to `/api/version.json`).
3. Deploying/restarting your own Node server: see [server/README.md](server/README.md)
   (English: [server/README-en.md](server/README-en.md)). The server **supports single-instance
   deployment only** — rate-limit counters, sessions and IP blocks live in process memory, so PM2
   cluster mode / multiple replicas make state drift.
