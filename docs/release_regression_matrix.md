# 发版稳定性回归矩阵（P1-1）

1.6.3～1.6.7 的更新日志几乎都落在同一族问题上：数据库打不开/锁死、长后台卡在「加载通知记录」、
离线队列丢历史、启动页无界等待。这些缺陷的共同点是**只在特定设备状态**下出现，单测与页面点击
闸门都覆盖不到。本矩阵把「长锁屏 / 弱网 / 低内存 / 进程被杀」四类状态固定成发版前必跑项。

## 执行方式

- 发版脚本已内置：`bash .github/scripts/release_local.sh <A.B.C>` 的**阶段 6.5** 会调用
  `bash .github/scripts/release_matrix.sh`；任一类场景红 ⇒ 本轮发版失败。
- 单独复跑：`bash .github/scripts/release_matrix.sh [APK 路径]`
  - 不传 APK 时优先取 `build/app/outputs/flutter-apk/v*/notice_all_*.apk`，其次取 x86_64 包；
    都没有时构建 debug x64 包（只验逻辑，不代表 release 包）。
  - 脚本会启动一个 headless 模拟器，装包、跑四类场景，结束后关闭自己启动的模拟器。
  - 脚本只允许操作 `emulator-*`；发现真机 serial 会直接停下，不会清任何数据。
- 脚本用完就关模拟器，不会挂在后台；四个场景合计约 2～4 分钟（`MATRIX_LOCK_SECONDS` 默认 30s）。

## 自动化覆盖（每次发版必跑）

| 场景 | 模拟方式 | 通过判据 | 证据 |
| --- | --- | --- | --- |
| 进程被杀 | 退到后台 → `am kill`；若被前台服务保护则 `am force-stop` 兜底 | 重新打开后 60s 内画出首帧；进程存活；无 `FATAL EXCEPTION` / `ANR in com.fnthink.notice` | `PASS 进程被杀-重新打开`、`ActivityTaskManager: Displayed ...` |
| 低内存 | 前台运行时 `am send-trim-memory <pid> RUNNING_CRITICAL` | 触发后进程仍存活、页面仍是前台；再次进入后无崩溃/ANR | `PASS 低内存-*` |
| 弱网 | 模拟器控制台 `network delay gprs` + `network speed gsm`；不可用时退回关闭 wifi/data 并验证 ping 不通 | 限速/断网状态下冷启动 60s 内画出首帧；恢复网络后进程存活、无崩溃 | `PASS 弱网-冷启动`、`PASS 弱网-恢复网络` |
| 长锁屏（短时） | `input keyevent POWER` 熄屏，保持 `MATRIX_LOCK_SECONDS`（默认 30s），唤醒并解锁 | 唤醒后能回到应用、进程存活、无崩溃/ANR | `PASS 长锁屏-唤醒` |

判红口径：任何一项 `FAIL` 都让脚本退出码非 0，发版脚本按硬闸门处理。场景因环境限制**没跑成**
按 `SKIP` 处理并默认同样判红（`MATRIX_ALLOW_SKIP=1` 只用于调试闸门本身，不是发布许可）。

## 人工必须补做（自动化替代不了）

| 场景 | 步骤 | 观察点 | 记录 |
| --- | --- | --- | --- |
| 长锁屏过夜 | 真机插电、锁屏 ≥8 小时（期间有消息进来） | 解锁后通知记录可打开；历史页不卡在「加载通知记录」；离线队列不丢 | 记录机型 / 系统版本 / 结果 |
| 真实弱网 | 地铁、电梯、弱信号区各待 10 分钟，前后各发一条测试消息 | 恢复网络后队列自动补发；不重复、不丢；启动页不无限转圈 | 记录网络类型与补发耗时 |
| 低内存真机 | 开发者选项 → 后台进程限制 1 个；再开相机/地图压内存 | 应用从后台回来仍可打开历史；服务被系统杀掉后能重新拉起 | 记录机型与系统版本 |
| 厂商后台清理 | 小米/华为/OPPO/vivo 各一台，锁屏放置 2 小时 | 常驻通知还在；通知监听/短信转发没有静默失效 | 记录厂商与系统版本 |
| 覆盖安装升级 | 用上一版 APK 装好并产生历史 → 直接覆盖安装本版 | 首次打开能完成迁移；历史条数一致；失败时出现「恢复迁移前备份」入口 | 记录升级前后条数 |
| 迁移失败回滚演练 | 仅在测试机：人为破坏迁移（如改 dbVersion 前先备份当前库）后启动 | 提示里有恢复入口；恢复后原库与新库都还在磁盘上，没有被清空 | 记录备份文件名与结果 |

## 与迁移备份的关系

数据库迁移的「迁移前自动快照 + 恢复入口」在应用内实现（见 `database_helper.dart` 与
`main_page.dart`）。本矩阵的「覆盖安装升级」与「迁移失败回滚演练」两行专门验证它：
自动化脚本只能保证升级后能冷启动，**能不能把历史救回来**必须由人工在测试机上看一眼。

## 结果留档

发版前把 `release_matrix.sh` 的末尾汇总（`PASS/FAIL/SKIP` 与四行 `PASS 场景-*`）连同人工项结果
贴进发版记录；只在全部为 PASS、且人工项都记了机型与结果时才允许打 tag。
